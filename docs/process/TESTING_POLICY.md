# 测试边界与执行策略

生效日期：2026-10-15。依据：用户明确要求按必要性划分测试，避免标点、样式和每次编辑前的机械测试。本规则优先于技能中的通用 TDD 要求。

## 1. 总体原则

采用风险驱动的行为验证：前端以关键交互集成测试为主，Rust 以复杂规则单元测试和数据/协议集成测试为主，桌面端到端只保留关键真实链路。

不以覆盖率、用例数量或每个函数都有测试作为目标。不要求每次编辑前运行测试，不强制所有需求先写失败测试。验收条件描述应达到的行为，不代表每条都要单独编写自动化用例。

测试应回答：防止什么实际故障、为什么现有验证不足、最合适在哪一层检查。同一风险已有充分保护时，不为每层重复建用例；只有不同层能暴露不同故障时才增加检查。

## 2. 改动边界

| 改动 | 新增自动化测试 | 合适的验证 |
|---|---|---|
| 普通提示文案、标点、注释、说明文档 | 默认不写 | 阅读修改；涉及链接/命令时按需检查有效性 |
| 颜色、间距、字体、圆角、装饰图标 | 默认不写 | 查看受影响界面；不默认建立截图快照或精确 CSS 断言 |
| 布局影响按钮可达性、遮挡、长文溢出或键盘焦点 | 有实际行为风险或重复缺陷时写 | 实际操作与可访问性检查；必要时交互回归 |
| 简单展示组件、纯透传封装、类型声明、生成代码 | 默认不单独写 | 按需类型/编译检查，由使用链路保护；不测试第三方内部实现 |
| 新的保存、采用、取消、删除、选择资料等交互 | 存在新增风险且现有用例未覆盖时写 | 围绕用户操作的集成测试 |
| 数据丢失、隐私泄露、错误引用、版本冲突、取消晚到覆盖 | 必须有自动化回归保护，复用或补充现有测试 | 在最能暴露问题的层验证；系统限制另做实机检查 |
| 数据迁移、备份/恢复、凭据、协议解析、路径权限 | 必须保护关键成功/失败与边界行为 | 真实存储/协议集成，关键规则单元测试及平台验证 |

按语义判断，不按文件后缀判断。例如普通标点不测，但 CSV 引号、路径字符、搜索语法、Unicode 偏移属于数据规则，需要相应测试；颜色装饰不测，但颜色若是状态唯一信息，应检查可理解性。

## 3. 前端如何测

重点覆盖：保存失败不能显示已保存；采用建议不覆盖原文；选定资料范围正确；取消生成后结果不能进入正式稿；原文/草稿切换不丢编辑内容；删除影响与确认有效。

测试用户看见的状态及操作结果，不断言 React 私有 state、Hook 调用次数、组件拆分、CSS class、完整 DOM 快照或普通文案逐字匹配。优先按角色和可访问名称定位；按钮改名可能需更新定位，但无需为标点建立独立用例。确属产品契约的警告含义、字段或协议文本可做针对性断言。

组件集成测试可以替代 Tauri IPC 边界，用受控响应验证成功、失败和延迟；不能把 mock 成功当作 Rust 保存或真实桌面通信成功。涉及实际持久化的验证交给 Rust 集成与少量桌面链路。

前端单元测试限于有分支/边界且有业务价值的纯规则，如版本冲突判断、选择范围和状态转换。常量、简单拼接、第三方编辑器内部功能不逐项测试。

## 4. Rust 如何测

单元测试保护容易出错、输入可控的规则：证据/来源校验、版本判断、状态机、Unicode/短词检索规则、导出转义、归档路径拒绝、流式分片解析。可使用代表性表格用例覆盖边界，不穷举任意组合。

集成测试通过业务公开接口连接真实临时 SQLite 和文件目录：保存/重开、事务回滚、引用稳定、迁移、图片关联、备份恢复、损坏包不覆盖原资料。数据库错误不能全部用 mock 替代。

模型协议用本地受控 HTTP 服务或进程协议夹具检查分片、截断、失败和取消；日常回归不依赖真实模型输出、外网或账户费用。Codex 真正权限、系统凭据和安装升级用平台验证，不能仅凭协议 mock 宣称安全。

不为每个私有函数、getter、透传命令或外部库行为单独写测试。测试可以调用私有复杂规则，但 Rust 允许测试私有接口不等于所有私有接口都必须测。

## 5. 实际操作、端到端与模型评审

端到端保留少量完整链路：记录含图片并重开；选择资料生成独立稿件并取消；跨篇主题到策划导出；备份恢复。其余边界尽量在更快的规则/集成层验证。

界面样式通过实际查看验证；只有经常回归且普通操作难发现的问题才考虑视觉自动化，不建立整站截图快照。系统文件选择、中文输入法、凭据弹窗、签名安装与升级在对应平台检查。

真实模型测试用于入口首次接入、协议/认证重要变化和必要发布验证，须使用合成资料及获准服务。文案品质、个人风格由有限样本人工评审，不对生成全文做快照，不自动反复调用模型追求通过。

## 6. 什么时候运行

| 时机 | 执行范围 |
|---|---|
| 编辑前 | 默认无需跑测试。缺陷可先用最小复现确认现象；高风险缺陷适合先加失败回归，不要求先跑全套 |
| 一组相关改动完成后 | 跑受影响的规则/集成测试和必要类型/编译检查；纯文档/装饰改动不触发应用全套 |
| 功能完成 | 检查对应验收行为，必要时实际操作；不重复刚已通过且输入未变的检查 |
| 跨模块重构、依赖升级、共享契约变化 | 扩大到相关模块及关键链路；影响面不明才运行更广回归 |
| 合并或稳定交付节点 | 运行快速自动化套件及构建；端到端按受影响链路选择 |
| 正式发布 | 快速套件、构建、关键端到端、迁移恢复和双平台发行检查；耗时专项按对应能力变化安排 |

新增高风险规则可选择先写测试，也可以实现后补齐，完成交付前必须有有效保护。不要把“先测试”变成每次改代码的许可步骤。

## 7. 控制时间和资源

- 本地开发默认用定向执行，不后台常驻全套测试、浏览器矩阵或性能扫描。
- 不默认采集覆盖率、执行压力测试或遍历所有平台/模型组合；这些只在对应风险、缺陷或发行节点运行。
- 故障有确定性地复现与修复，不反复重跑直到偶然变绿；不自动增加大超时掩盖卡住。
- 跑过且与后续改动无关的成功检查不重复。失败、输入变化或新风险才扩大/重跑。
- 记录耗时；稳定变慢的用例检查是否重复、外网依赖或层次不合适，再优化，不删除仍必要的保护。
- 不用任意时间上限跳过数据安全验证，也不把并行测试开满机器当作默认方案。

## 8. 记录与维护

每次交付用一句话说明新增/复用哪些保护、运行哪些检查及结果；没新增测试时说明是文案/样式等低风险或已有保护，无需逐个编辑写报告。未运行的范围明确标注。

重复、只锁实现细节、只验证固定文本或 mock 的测试应合并/删除；保留实际风险对应的行为保护。高风险测试删除前需确认替代保护仍能检出原故障，不能用降低断言掩盖失败。

功能规格模板中的“验收场景”用于产品验收；另注明自动化/实际操作/人工评审中的适用方式。性能数据集是专项验证，不是每次提交的必跑任务。

## 9. 调研依据

Testing Library 强调从用户操作与输出验证，避免组件内部实现细节。这支持本项目前端集成优先的选择。[官方原则](https://testing-library.com/docs/guiding-principles/)

Rust 官方区分模块隔离的单元测试与公开接口的集成测试，没有强制为所有私有接口建用例。本项目按规则和存储风险分工。[官方测试组织](https://doc.rust-lang.org/book/ch11-03-test-organization.html)

Testing Trophy 的提出者强调测试带来的信心与维护成本，前端以集成测试为重。本项目结合桌面数据风险制定上述策略，并非照搬固定测试比例。[作者原文](https://kentcdodds.com/blog/write-tests)

已按项目规则通过 ctx7 CLI 查询 Rust 与 Testing Library，再读取相关官方页面。以上资料提供方法依据，具体边界和执行频率由本项目用户要求决定。
