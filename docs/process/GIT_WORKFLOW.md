# Git 与远程协作流程

建立日期：2026-10-15。远程：[NotionNest/LifeStory-Studio](https://github.com/NotionNest/LifeStory-Studio)，私有仓库。本地默认分支为 main，远程为 origin。

## 日常流程

采用 main + 短期工作分支，不另外维护长期 develop 分支。

1. 开始任务前检查工作区，先保留已有修改，再同步 main；不自动覆盖或丢弃未提交内容。
2. 按任务建立 `feat/主题`、`fix/主题`、`docs/主题` 或 `chore/主题` 分支；一个分支围绕一个可审阅成果。
3. 在分支实现，按测试边界执行相关检查，并更新功能文档与进度。
4. 用 `feat:`、`fix:`、`docs:`、`chore:` 等前缀提交，说明具体变化；不使用“update files”作为唯一说明。
5. 用户授权远程交付的任务可以推送分支并创建 PR；发布、合并仍依据该任务的明确授权执行。
6. PR 使用模板说明最终行为及验证，确认检查和评审后 squash merge 到 main，删除已合并的远程工作分支。

本次初始化例外：将已有完整工程和工作流程推到 main，并完成首次 CI 暴露问题的修复；初始化交付结束后按上述分支流程工作。

## 保护数据与历史

- 提交前检查 staged diff 和文件清单；构建产物、node_modules、资料库、密钥与私人日记不得进入仓库。
- 提交依赖锁文件、必要图标与迁移。跨平台文本使用 LF，图片按二进制处理。
- 不对 main 强推，不自动执行 reset --hard 或清理用户文件。不对已共享历史做 rebase/amend 后强推。
- 对已经提交的错误优先用新的修复提交或 revert 保留历史；真正删除私密历史需要单独处理和明确授权。
- 不把登录令牌写入 remote URL、仓库配置文件、CI 或文档，使用已有 GitHub 登录与凭据管理。

## GitHub 检查

Checks 在涉及代码/构建配置的 PR 与 main 推送时运行，纯文档改动默认不启动双平台构建；支持手动运行。新提交取消同一分支过时的检查，缓存 npm/Cargo，Cargo 工作线程为 2。

macOS 与 Windows 检查内容：锁定依赖安装、类型和格式、现有存储集成用例、Rust 静态检查以及桌面编译。当前没有为了 CI 凑数量加入前端样式用例，不调用真实模型、读取用户资料或上传安装包。

CI 编译通过不能替代真实系统交互、签名、公证、安装升级或 AI 权限验证。运行状态以 GitHub 实际结果为准，未完成不能写成通过。

仓库采用 squash merge 并自动删除已合并分支。分支纪律与服务器强制保护是不同概念：本次不声称已开启受保护分支；后续设置 required checks 时，要同时处理纯文档 PR 跳过工作流的情况，避免永久等待。

## 你如何使用

你可以直接说：

> 从 main 开一个分支完成这个任务，按测试边界验证后提交，并创建 PR 给我看。

> 查看这个 PR 的检查结果和修改，确认满足需求后合并。

AI 负责执行 Git 与文档更新，向你报告分支、提交、PR 链接和实际检查结果。远程仓库保持私有，公开仓库或正式发布另行决定。
