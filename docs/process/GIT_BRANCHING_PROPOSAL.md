# develop 与预发布分支方案

2026-10-16。用户提出增加 develop 和预发布分支、希望更完整流程。本文件是可审阅提案，尚未创建分支、修改 Actions 或仓库设置，也未提交/推送/修改 PR；现行配置仍见 GIT_WORKFLOW.md 与 .github/workflows/。最新本地保存功能修改完整保留。

## 当前问题

1. PR #2 前序成果已经随 #1 合并，范围重复；#3 有冲突、说明仍是旧保存方案，最新功能只在未提交工作区。
2. 本地 main/origin/main 缓存未同步到真实远程 main；不能按旧图直接继续叠加依赖分支。
3. main 没有强制保护/required checks。当前仅允许 squash 合并；不能直接把该限制套用到长期分支之间。
4. Checks 只匹配目标 main 的 PR 和 main push 的特定路径。一个代码 PR 在创建、更新、重新打开时可运行，合并后的 main push 又可运行，因此不只是每次合并时一次。只改文档可能被路径过滤跳过；PR 已含代码时，后续仅文档提交也可能再次触发。
5. [skip ci] 曾混入 #1 的 squash 说明，有误跳过代码检查风险；整工作流因路径/标记跳过也可能令 required check 永远 Pending。
6. 类型/前端交互等检查在双平台矩阵中重复执行。尚无预发布包、版本号/标签、签名及安装升级交付链；桌面 compile 不能等同发布就绪。
7. 图片验证工作流另按 push 路径触发，未来也需纳入统一门禁，避免只有工具代码变化却未检查或重复触发。

## 分支职责

- main：正式发布基线，仅接纳通过发布验收的候选或紧急修复。
- develop：已完成且已验证功能的集成线；后续功能从这里分支，经 PR 合入这里。
- release/<版本>：从 develop 切出的每次发版预发布线；只接纳该版本的缺陷修复、版本信息和发布准备，不接收新功能，发版后删除。
- feat/*、fix/*、docs/*、chore/*：短期任务分支，通常回 develop；候选缺陷从对应 release 分支出发并回该分支。
- hotfix/*：从 main 出发的紧急正式修复；修复进入 main 后同步 develop 及仍在维护的候选分支。

不默认再加长期 staging、beta、test 或独立测试分支。预发布是 release/<版本> 的用途；如果以后需要长期内部试用渠道，再明确渠道而不是增加同义分支。

## 流转与合并

常规：develop → feat/任务 → PR 回 develop；发版：develop 切 release/<版本> → 候选验收 → PR 回 main → 对正式发布提交打标签 → main 回合 develop。

任务 PR 默认 squash，使一个成果在集成线上有一个清楚提交。release→main、main→develop 等集成/回流采用保留祖先关系的 merge；不能全部 squash，也不强推共享分支。为此仓库需允许 merge commit，并配置不同 PR 的目标/来源规则。若选择其他保留祖先的方式，需另作明确定义，不能只改一个开关就视为流程已完成。

发布后回流必须带回候选期间所有修复和版本变更；活跃 release 要纳入 main 的紧急修复。清理分支前确认没有仍依赖它的 PR、未回流修复及未提交工作。

## Actions 与成本边界

建议把检查、预发布构建、正式发布分开；不是每次 push 都跑全套矩阵。

| 时机 | 检查/产物 |
|---|---|
| 本地一组相关修改完成 | 按风险执行受影响验证，保持既有测试边界 |
| 指向 develop 的代码 PR 创建/更新 | 通用类型、格式与前端交互集中跑一次；涉及桌面/存储的代码进行 macOS/Windows Rust 测试、Clippy 与集成编译 |
| 纯说明文档 PR | 轻量文档/变更检查，桌面矩阵不启动；稳定门禁仍给出结果 |
| develop 合并后 | 集成状态核对，不无条件重跑刚通过的全部套件；可按明确需求手动生成内部构建 |
| release 候选合入或产生新版候选 | 双平台完整相关回归、迁移/恢复、可安装候选包；同一候选提交避免 PR/push 两次重包 |
| release → main PR | 验证目标合并结果、发布清单和候选证据；若相对验证候选有代码变化，重新验证，不凭分支名复用绿灯 |
| 正式版本标签/获准发布 | 校验标签提交、版本、候选证据及产物来源，再进行正式构建/签名/发布；有安全环境审批。版本变动或产物不一致时不直接复用候选包 |

固定稳定的 required gate 在每个 PR 都产出结论，内部按变更决定重任务；不在入口用 paths/skip 标记绕过整个必需门禁。依赖安装使用锁文件、缓存，取消同一 PR 的过期任务。真实模型、压力测试、全部 UI 快照不纳入例行检查。

main push 不再无条件重复整套 Checks，但必要的版本、门禁和产物来源核对仍保留。若允许绕过 PR 直接推 main，就不能同时依赖 PR 门禁作为唯一保护；建议禁止此路径。

## 发布保护

main/develop/release 通过 PR 和稳定门禁更新，限制强推/删除及绕过行为；具体服务器保护以账号权限和可用套餐能力核实，不能写了规则就声称已强制执行。单人项目不设本人无法满足的自我审批要求，合并与对外发布仍由用户明确授权。

每个候选使用 rc 版本/标签，正式发布用正式版本/标签，并统一 package.json、Tauri 与 Cargo 的版本维护。预发布与正式应用需区分应用标识/数据目录，避免试用包覆盖稳定应用或直接升级稳定资料库；签名/公证、Windows 安装升级及迁移/备份恢复需在对应发布节点验证。

回退 Git 提交不等于回退已经迁移的用户数据库；发版故障处理必须尊重 schema 兼容门槛和已验证备份恢复，不自动对用户资料做降级或覆盖。创建分支、合并 PR、打标签、构建包及发布属于不同操作，不互相视作授权。

## 迁入新流程的顺序

先安全保存全部未提交修改；核对真实 main 内容；处理重复 #2；整理 #3 与最新本地修订的边界和冲突。之后明确 develop 的初始基线、候选版本，再落地分支、合并设置、Actions 和保护规则。未确定版本前不凭空创建某个 release 版本分支。不在未保存工作区上切换/重置，不自动删除旧 PR/分支。
