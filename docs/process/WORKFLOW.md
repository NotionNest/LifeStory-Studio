# 个人产品与 AI 协作开发工作流

状态：已建立，待用户审阅。日期：2026-10-14。

## 采用的方法

采用规范驱动开发：先写清用户要完成什么，再确定技术方案，随后拆任务、实现和验证。产品负责人是用户；AI 负责整理、研究、设计、开发与验证，并将结果落到可审阅的文件。

这是一套项目工作流程，不是应用运行时框架，也不是第三方工具安装结果。“最主流”缺少统一统计口径，本项目采用有官方实践支持、适合长期独立产品的共同方法。

GitHub Spec Kit 提供从规范到技术规划、任务、实现与收敛的结构化过程。本项目借鉴这种阶段划分，具体文件按产品需要组织。[官方项目](https://github.com/github/spec-kit)

Anthropic 的长期代理实践强调功能清单、会话间进度记录及验证实际交互。本项目据此保留任务状态和验证证据。[官方实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

## 阶段与交付

| 阶段 | 输入与工作 | 交付 | 进入下一阶段的依据 |
|---|---|---|---|
| 产品定义 | 原始需求、已知问题、用户目标 | PRD、未决事项 | 用户认可产品方向与核心范围 |
| 体验与技术方案 | 关键流程、平台/AI/隐私决策、当前文档研究 | 体验方案、架构、技术选型与决策记录 | 关键未决事项解决，方案可审阅且满足需求 |
| 开发环境 | 已确定技术方案 | 可运行的 Tauri 项目、开发说明、必要检查 | 本机启动与核心环境检查有证据 |
| 功能规划 | REQ 需求与架构约束 | 功能规格、关联任务、验收场景 | 当前功能具备明确行为和依赖 |
| 实现与验证 | 当前功能规格与任务 | 完整功能、针对性检查、实际交互证据 | 满足验收条件，问题处理完成 |
| 发布准备 | 功能验证结果与发行目标 | 安装包、数据升级/备份方案、发布检查 | 目标平台安装与升级验证完成，发布授权明确 |
| 使用与改进 | 实际使用反馈 | 缺陷/改进任务与需求更新 | 反馈关联原有需求，下一轮有明确目标 |

按阶段推进是为了控制依赖，不代表降低最终品质。正式发布范围在产品决策后确定，不把开发顺序当作功能裁剪。

## 一次工作会话

1. 读取项目状态、PRD、决策和当前功能规格。
2. 找到获准且依赖满足的任务，说明本次成果与验证方法。
3. 必要时查阅当前官方文档；在授权范围内完成具体工作。
4. 按 [测试边界](TESTING_POLICY.md) 选择验证：相关改动完成后做针对性检查，不要求每次编辑前测试。真实持久化与系统行为不能仅靠 mock 验证；普通文案/装饰只做必要查看。
5. 更新任务状态与证据，记录未解决事项和下一步。

用户审阅集中在方向、体验和重大技术方案节点；常规任务无需反复请求许可。

## 文件职责与变更

- PRD 是产品行为的依据；原始对话整理保留来源，不与 PRD 平行维护需求。
- DECISIONS 是待决策事项和确认记录的入口；重大技术决策另建决策文件并链接。
- STATUS 是进度的唯一入口；功能规格记录详细行为，任务表只跟踪状态与依赖。
- 变更包含：触发原因、受影响 REQ、决定人及依据、对方案/任务/验证的影响。获准后同步更新相关文件。
- 架构和技术文档在下一阶段形成，当前不预填技术结论。

## 状态定义

`待开始 → 进行中 → 待验证 → 已验证`；文档交付可为 `已编写·待审阅`。真正需要外部条件或用户决定的任务标为 `受阻` 并注明条件。已验证不等于已发布。

每项验证记录检查对象、步骤或命令、实际结果、日期及证据位置。AI 输出质量以真实用户评审为最终依据，测试只能验证约束和行为，不能宣称已经证明“没有 AI 腔”。
