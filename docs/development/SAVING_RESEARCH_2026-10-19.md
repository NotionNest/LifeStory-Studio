# 保存设计复核与编辑器调研

日期：2026-10-19。关联 REQ-01/02、LIB-03。针对用户对前次审查的质疑，重新核对代码、官方资料与合成测量。本次仅调研和建议，不修改产品行为，不提交/推送或启动 LIB-04。下文参数与实现调整尚非用户确认。

## 结论

保留现有本地 SQLite、单连接工作线程、自动合并写入、事务回执与历史独立的整体设计。没有证据支持推翻存储架构。需要收敛的是编辑器离开边界与重试调度，而不是加入更多保存层、全局文档框架、操作日志或协作协议。

前次审查证明了受控异步时序下的丢失，但没有测量正常 GUI 的触发概率。把它解释成用户经常遇到的问题没有依据。暂忙自动重试同样属于低频异常；当前单连接不会因用户同时浏览列表与写作而自己争抢写锁。

## 三种编辑器的公开做法

| 产品 | 官方资料可以确认的行为 | 对本项目的意义 |
|---|---|---|
| VS Code | 默认手动保存；可按延迟（默认 1000ms）、焦点变化或窗口变化自动保存；Hot Exit 处理未保存内容；working copy 统一处理内容身份、dirty、保存与备份 | 输入模型、视图和落盘并非同一件事。切换显示内容不应意味着未保存内容失去所有者 |

## 当前实现究竟怎么保存

1. 输入先更新 Tiptap/React 内存状态，增加编辑序号。
2. 停止输入 300ms 时发起保存；持续输入则最多 2 秒尝试一次。没有修改时不周期性写库。
3. 同一编辑器最多一个在途保存，较新修改在下一次保存追平。保存通过 IPC 转交 Rust，再进入单个连接的队列。
4. SQLite 事务更新当前正文、必要标签/检索、版本和最新请求回执，提交成功后才标记已保存。
5. 当前使用 WAL + synchronous=FULL，每次提交有额外 WAL 同步。SQLite 页面写入不等于每次重写整个数据库，但正文改变时应用确实处理完整正文及搜索派生数据。
6. 历史只在重新进入编辑时固定上一轮，独立于自动保存。新编辑不再生成第二套恢复草稿。

所以“实时”是近实时自动保存，不是每个按键已耐久落盘。每次重置 JS 计时器只改内存调度，不触发磁盘 I/O；活跃计时器数量有界，并非每键累积新计时器。不能凭这些计时器断言资源浪费。更值得衡量的是完整 JSON 校验/序列化、全文索引维护、回执内容副本与每次事务同步。

持续高频输入时约每 2 秒尝试一次；输入停顿都略长于 300ms 时，可能接近每秒 3 次自动保存触发。这是正常调度估算，不包含手动/离开提交、不等于物理设备写入次数或 IOPS，也未计入在途耗时。当前缺少真实写作与设备 I/O/能耗采样，不能据此认定频率已构成问题。

## 问题 1：真的能触发吗

已确认：受控 React 集成测试中，延迟目标读取，在仍展示的旧编辑器输入，再完成切换，可导致新输入未经 save 被卸载。该测试是确定性正确性反例。

未确认：没有用真实键鼠在不插入延迟的生产桌面包中稳定复现，没有概率或用户发生率数据。短记录在快磁盘上的窗口很窄；大记录、排队的数据库任务或慢设备可能延长窗口，这是代码和测量支持的推断，不是线上事故证据。

修正不需要建立 VS Code 规模的框架。建议在切换开始后完成当前组合输入、结束旧内容接受新编辑的阶段，提交最新内容，成功才更换编辑器；失败留在原记录。正常切换无确认对话框；仅失败时保留已有重试/另存/放弃流程。先以局部生命周期修正评估，不为这个边界加入全局文档仓库和后台未保存记录集合。

## 问题 2：数据库暂忙与重试

storage.rs 只有一个应用数据库连接和串行任务线程，且设置了 busy_timeout(2s)。当前文字保存、列表读取、检查点按队列执行，不是彼此并行的 SQLite 写事务。慢、磁盘满、权限不足和锁竞争是不同情况，不能统称“数据库忙”。

其他进程/连接写同一数据库（如另一个应用实例、数据库工具持有写事务），才是本项目更具体的 BUSY 来源；WAL 还存在跨连接关闭/恢复的短暂独占情况。当前未接入单实例插件，但这不等于日常一定会启动多实例。

等待超时也不是保证每次先等两秒：SQLite 会在可能形成死锁或读事务升级的部分情况立即返回 BUSY。独立合成测试中，另一个连接 BEGIN IMMEDIATE 持有写事务后，当前保存在约 1.38ms 返回 database is locked；没有真实资料库操作。

计时器延期缺陷是真实的，但只有先遇到指定暂忙/中断错误，随后连续输入、未主动重试/离开才进入该路径。它不是“当前每次保存都忙”。保留有上限间隔的重试是合理的；独立维护已经确定的重试截止点即可，不需要新增重试框架。不能让每次输入把到期重试反复延后。

SQLite 依据：[错误码](https://www.sqlite.org/rescode.html)、[busy_timeout](https://www.sqlite.org/c3ref/busy_timeout.html)、[WAL 并发与 BUSY](https://www.sqlite.org/wal.html)、[同步设置](https://www.sqlite.org/pragma.html#pragma_synchronous)。已按项目规则通过 ctx7 CLI 的 library 与两条分主题 docs 查询核实。

## 建议的最终方向（待审阅）

- 保持单一自动保存链路、串行写入、版本校验、SQLite 事务、真实保存状态和现有历史规则。
- 保存调度采用短防抖和持续输入上限。300ms 不是正确性的必要条件；如要降低频率，建议起点为停止输入 800ms、持续输入 2 秒，随后按实际使用和长文采样决定。本次不自行更改已实现参数。
- 离开时由一个局部流程完成输入收口、保存和切换；成功不弹窗，失败才呈现操作。
- 暂忙重试截止点独立于输入防抖；不扩展错误类型、配置项或额外保存层。
- 保留 WAL + FULL。NORMAL 可降低提交同步成本，但会改变断电后的耐久性边界；没有实测瓶颈和明确需求前不做此取舍。

本地单用户文字编辑没有一套因“更新”就普遍最优的存储方案。成熟方案的共同点是编辑立即响应、后台合并写入、保存结果真实、内容生命周期明确。当前设计总体符合这个方向，最合适的是收敛实现与补齐边界，而不是升级成云协作系统。
