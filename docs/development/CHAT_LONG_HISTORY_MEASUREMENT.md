# 长聊天数据与渲染策略测量

2026-10-28，REQ-11/12/13 / TASK-11。用户授权先用合成长历史测量，再决定分页、增量读取或虚拟化。本轮交付测量与工程决策，不将实验原型视为已接入产品的优化。

## 方法与有效性

- macOS arm64，Chrome 156.0.8078.49 无头模式，React 19.3.1 / Vite 生产构建；1200×900 视口，1000×800 聊天容器。实际 Tauri WKWebView / Windows WebView2 未测量。
- 100 / 1000 / 5000 条合成消息，交替用户/助手，单条 1024 个中文字符，无图片、无真实日记、无付费模型。挂载真实 ChatMessageList、MessageDetails 与原 MessageScroller，保留现有 content-visibility；仅用合成 Context 隔离网络/会话干扰。
- 每个浏览器案例 3 次挂载，每次 3 次更新。表中取中位数。同一浏览器连续运行，后续案例已预热；组件挂载成本不等同应用冷启动时间。DOM 规模使用 querySelectorAll("*") 统计元素，不包含文本节点。`mountWorkMs` / `updateWorkMs` 是 flushSync 包含的主线程同步工作；`mountMs` / `updateMs` 等待两次 requestAnimationFrame，用于观察更新稳定时间，短案例存在约 33ms 的人为帧等待下限，不将它当作实际渲染工作。
- 浏览器每次更新模拟收到完整 JSON 后重新解析。任务增量原型只替换 task 并保留历史 message 对象引用；memo 原型提取消息行；100 条原型只把尾部窗口序列化并挂载。后两者尚未实现后端分页、滚动加载或搜索定位。
- 原生侧在独立临时 SQLite 中通过真实 DatabaseWorker.ai_workspace 测量读取与 serde_json 序列化，每档 5 次；文字为 1029 字符。使用 **debug test**，不可当作 release 安装包或完整 IPC 耗时。另测现有 `(record_id, sequence)` 索引下最近 100 条内容查询，该查询不包含完整 workspace 元数据/任务装饰。
- 初次临时入口出现 /tmp 与 /private/tmp 模块身份不一致，Context 无效；该轮数据全部丢弃。修正路径后加入页面 DOM 规模和 pageerror 校验，最终存档案例均实际渲染且无页面异常。未采用空页面数据推导性能收益。

## 当前实现：成本随历史增长

| 消息数 | 完整 JSON 大小 | DOM 元素 | 首次主线程工作 | 首次稳定 | 单次完整更新主线程工作 |
|---:|---:|---:|---:|---:|---:|
| 100 | 314,132 B | 925 | 12.8ms | 32.8ms | 5.7ms |
| 1,000 | 3,141,482 B | 9,025 | 72.0ms | 91.4ms | 43.3ms |
| 5,000 | 15,715,482 B | 45,025 | 407.7ms | 489.0ms | 247.9ms |

5,000 条 JSON.parse 的各次样本为数毫秒量级，主要浏览器问题是历史行创建/协调与 DOM 规模，不是单纯 JSON.parse。现有 content-visibility 减少离屏布局绘制，但没有消除 React 行更新和 DOM 挂载。

5000 条完整快照约 15 MiB。若按配置的 400ms 节拍反复发送，理论数据量约 37.5 MiB/s；这是名义节拍下的估算，不是测得的 IPC 吞吐。当前串行轮询会跳过未完成读取，实际频率可能更低。

## 策略对照：5000 条

| 隔离实验 | 初次传输 | 更新传输 | DOM 元素 | 首次主线程工作 | 更新主线程工作 |
|---|---:|---:|---:|---:|---:|
| 原实现完整快照 | 15,715,482 B | 15,715,482 B | 45,025 | 407.7ms | 247.9ms |
| 只换 task，历史引用不变 | 同上 | 96 B | 45,025 | 386.1ms | 215.0ms |
| 任务更新 + memo 消息行 | 同上 | 96 B | 45,025 | 397.7ms | 6.9ms |
| 尾部 100 条窗口 + 任务更新 + memo 行 | 314,552 B | 96 B | 925 | 13.7ms | 0.5ms |

96 B 只是本实验很短的 task 投影，不代表将来完整增量协议固定为 96 B；真实任务正文增长、来源和关联元数据仍有开销。100 条仅是测量窗口，不是已经确认的产品容量上限。堆采样受 GC 与前序案例影响，未据此宣称确定的内存降幅。

只换为 task 接口不能单独解决问题：消息列表仍映射全部历史行。memo 行显著降低流式更新成本，但不改变首次完整传输/挂载。限定驻留窗口才能同时控制首次成本和 DOM；仅在前端收到全量后 slice 不会减少数据库或 IPC 成本。

## 决策与实现边界

工程选择：**游标分页 + 任务与新增消息增量读取 + 动态高度虚拟化（有界 DOM）**，并配合消息行复用。保留当前连续滚动体验。不单独依赖 content-visibility、memo 或只换 task 轮询。

1. 首次打开查询元数据和尾部一页；依据 sequence 与唯一消息 ID 确定稳定游标。消息页面必须在 SQL 层限量，不在完整 workspace 返回后再切片。
2. 生成期间读取任务与游标之后的新消息，按 ID/sequence 去重，保留未变化消息的引用。来源失效、关联、预览与任务终态也要有明确刷新规则；不能只更新 task 后永久遗漏元数据变化。
3. 历史按需读取，并对驻留消息窗口设边界。不能“加载更早”时无限拼接，最终又挂载 45,000 个节点。窗口交换需保留可见消息锚点、焦点和上下文。
4. 搜索命中从后端查询目标附近窗口并核对所属聊天，不能因为消息未加载就误报已删除；“回到最新”读取尾部窗口。图片迟到改变高度、推理摘要展开、复制和辅助聊天宽度变化必须保留滚动行为。
5. 后端生成上下文与日记预览选材继续按现有规则读取完整授权历史；显示分页不能截断模型输入或把未加载消息当成不存在。保持唯一会话、P1 代次/请求顺序保护、队列串行与失败显式继续。

**虚拟化选择**：分页控制数据库/IPC/已加载数据，虚拟化控制 DOM 驻留，两者解决不同成本。现有聊天是连续滚动，正式方案选择动态高度虚拟化与分页配合，保留前后滚动和自动跟随；100条成本原型不作为“固定上一页/下一页”的产品交互。尚未选定或安装虚拟化库，也未验证其与 MessageScroller 的动态高度、锚点和自动跟随协议，接入必须覆盖上述交互，不能宣称本轮已完成虚拟化验证。

下一步应将上述边界转为消息窗口、搜索定位和滚动交互规格，再实施协议与 UI；本轮不直接替换生产 workspace 或删除现有滚动功能。此为工程建议和测量结论，不能标为用户已确认全部分页交互或长聊天已优化完成。
