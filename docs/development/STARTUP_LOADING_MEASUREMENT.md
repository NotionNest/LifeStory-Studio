# 桌面启动与加载边界实测

2026-10-28，REQ-12 / TASK-11。用户要求先测量桌面启动及首次打开页面，再确定加载边界。本轮交付真实 macOS 测量、边界决策及复现材料，未将原型接入产品。

## 测量方式与边界

- macOS 26.5.2 / arm64，真实 Tauri 2.12.4 + WKWebView；Vite 生产前端，**debug 原生程序**。未使用 Chrome 数据代替桌面数据，未测签名 release、Windows 或真实个人资料。
- 三个独立应用标识，各5次新进程；每组数据库由空开始，逐次增加一条合成空日记，因此首页分别有0–4条。每次都确认独立数据目录。只读扫描本机 CLI，不测试/调用模型或配置密钥。
- “启动”从宿主 spawn 到日记首页数据加载完成并等待两次 animation frame；“页面首开/再次打开”从 hash 跳转到目标控件出现再等两帧，包含真实离开准备、loader、模块加载和编辑器初始化。没有跳过保存保护；空日记不产生未提交草稿。
- 不清空 OS/WebKit 缓存，不能等同 OS 完全冷启动。两帧等待使轻页面有约25–30ms下限，差十几毫秒可能只是帧相位。每组只有5次，报告观察中位数和全部原始样本，不作统计显著性或固定提速承诺。
- 最终变体均用可见置顶窗口，所有构建完成后串行测量。先前一次测量与编译重叠，另一次遇窗口遮挡导致帧等待超时，均不进入最终结果；入口事件与可见性检查将问题定位到帧等待，不能当成产品启动卡死。

## 三种加载变体

| 变体 | 入口 JS | 首屏静态依赖闭包 | 首屏 JS 文件 | 全部 JS 文件 |
|---|---:|---:|---:|---:|
| 当前静态加载＋同一探针 | 1,219,724 B | 1,219,724 B | 1 | 1 |
| 非首页路由细粒度 lazy 原型 | 390,361 B | 770,595 B | 31 | 41 |
| 编辑器/历史合为单个延迟组 | 766,933 B | 766,933 B | 1 | 2 |

正常未注入探针的当前主 JS 约1.217 MB；上表三组含同一时序探针，不能将它和旧版1.215 MB直接当作代码增长比较。仅看细粒度原型的 index 会误以为首屏只需要390 KB，实际上其静态依赖闭包约771 KB。所有代码仍随桌面包分发，拆分也没有明显降低约73 MiB的debug应用包。

编辑器/历史的重型依赖为主要可延迟部分：细粒度原型中含 Tiptap/ProseMirror 的共享块约411 KB；集中原型将页面、编辑会话和编辑器依赖一起放入约454 KB延迟块。默认首页及窗口级业务状态不因原型卸载。

各组启动原始样本：

- 基线：3852、653、603、647、579ms。
- 细粒度：2869、667、713、730、725ms。
- 集中组：3304、522、540、668、689ms。

首次运行均有秒级样本，原因可能涉及原生/WebKit进程和系统缓存，未单独剖析；不能拿3852→2869宣称冷启动变快。后续样本范围重叠。当前数据**没有证明减少首屏JS带来桌面启动收益**；观察到的编辑首开增加约19–31ms，包含多种异步/帧调度因素，不把全部差值归因于网络或脚本解析。

CLI扫描约1.25秒是独立业务成本，页面本身约27ms已经显示。拆包没有降低本机发现/版本查询时间。API/CLI在本实验均无用户服务配置，含大量配置或真实聊天的成本不在本轮结论内。

## 为什么只改路由还不够

构建器实际报告了三处无效动态导入：

1. ChatWorkspace 仍由 DiaryChatDock 静态引入，辅助聊天让完整聊天/预览视图进入主布局依赖链。
2. AiSettings 同时导出 ApiSettingsSession 和表单，窗口级 SettingsSessionProvider 静态导入会话时也将表单留在首屏图中。
3. LocalCliSettings 同样将持久会话和视图放在一个模块，单独对路由写 lazy 不会推迟该模块。

不能为让分块生效而按路由卸载这些会话，否则会破坏输入、配置草稿、队列及离开保护。CSS与基础主题继续一次加载，本轮没有拆分样式或改变布局。

## 加载边界决定

**当前不采用“所有独立页面逐一 lazy”作为生产方案，也不为消除大包警告调整阈值或强行拆 vendor。** 独立路由不要求每个小布局都变成异步块。当前约0.65秒启动样本不能证明主包是主要瓶颈，分块会把部分成本推给首次打开页面。

确定后续边界如下：

| 边界 | 决定与理由 |
|---|---|
| 应用壳、默认日记首页、Root/ErrorBoundary、路径/小 loader、主题 | 常驻；避免首屏额外等待，loader可与重视图加载并行 |
| 窗口级聊天/设置/离开保护会话 | 生命周期常驻；仅有UI需求时再加载视图，不能按页面创建第二份状态 |
| 日记编辑/历史及 Tiptap | 同一业务重加载组；实测可延迟约450 KB，并保持跨编辑/历史的同一会话。首开有约几十毫秒代价，正式接入前评估用户指向日记时的意图预取，并验证直接历史地址/加载失败 |
| 完整聊天与辅助聊天 UI | 同一视图加载组候选；须同时解除主布局静态引入，复用唯一会话。仅在路由添加lazy无效，当前未测独立组收益 |
| API/CLI设置 | 会话逻辑保持常驻，视图先与会话解耦才可单独评估；扫描/模型目录读取成本分别测量 |
| 轻量布局、外观页等 | 保持同步，不因页面数增加而逐一产生小块 |

优先考虑集中业务边界，避免本次31个首屏共享文件的细碎化。编辑器/历史是已实测的候选重加载组，但在当前数据下**不立即将任何原型合入生产**；集中组也未证明启动快于基线。后续实施需明确首开/预取预算、异步失败呈现与路由保护验收，并补签名release及Windows测量后，才能宣称正式性能改善。
