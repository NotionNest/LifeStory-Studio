# LifeStory Studio 人类使用手册

更新：2026-10-19。

这份手册说明你如何使用项目工作流程和文档，与 AI 一起推进产品。桌面软件开发后的操作说明会另行编写。

## 你和 AI 各自负责什么

你负责表达目标、审阅关键方案、做产品决定，并反馈实际使用体验。

AI 负责整理和更新需求、研究方案、拆分任务、开发与验证，以及记录进度。你不需要手动填写或维护整套文档，直接在聊天中表达即可。

## 日常关注三个入口

| 文档 | 什么时候看 | 重点看什么 |
|---|---|---|
| [正式产品文档 PRD](product/PRD.md) | 确定方向、增加或调整功能时 | 描述是否符合你的想法，验收条件是否准确 |
| [待决策事项](product/DECISIONS.md) | 选择平台、AI 接入、隐私等方案时 | 选项、取舍和最终决定 |
| [项目跟进](tracking/STATUS.md) | 查看进度或隔几天继续工作时 | 已完成的成果、未解决事项和下一步 |

三个入口应足以了解产品范围、需要你决定的事项和当前进度。功能规格、页面流程和实施设计是下属细化资料，由 AI 维护；需要审阅具体行为时，从主文档链接进入，无需逐份追踪。项目跟进必须直接写出任务中文名称、状态与下一步，不能只给出 LIB 等编号让你自行查找。

编号阅读：TASK 是项目工作项；LIB 是 TASK-07 中资料库模块的子任务，两者不是平级。REQ 标识产品需求，DEC 标识决定。当前阶段、已完成成果与下一步统一查看项目跟进顶部；无需根据编号大小推断整个产品进度。

[工作流](process/WORKFLOW.md)、[AI 协作规则](../AGENTS.md)与[模板](templates/)主要供 AI 执行时使用。你可以查阅，但无需逐项填写。

## 如何推进产品

### 1. 审阅产品需求

先看 PRD，确认它描述的是你真正想做的产品。无需先理解技术细节。

直接在聊天里指出需要修改的内容，例如：

> 对话式记录必须加入，语音输入暂时不确定。请更新需求和待决策事项。

AI 应同步更新相关文档，区分已确认需求和待决定事项，不将建议自动当作你的决定。

### 2. 确认方向，进入方案阶段

当你认可产品方向时，可以说：

> 产品方向没问题，开始梳理架构和技术选型。

AI 会提供具体方案、选择理由、取舍及需要你决定的问题。你主要关注方案是否支持产品目标，以及费用、隐私和使用方式是否符合预期。

### 3. 认可方案，开始开发

方案审阅后，可以说：

> 按确认的方案搭建开发环境，并推进功能开发。

AI 应按功能规格与任务推进，提供可运行成果和验证证据，方便你实际体验。阶段性完成必须说明具体完成了什么，不能把文档、静态页面或未验证的代码当作完整功能。

### 4. 通过使用反馈改进

反馈可以用日常语言描述，说明发生了什么、你期待什么即可，例如：

> 主题推荐太泛，应该多引用日记里的具体事件。

> 我关闭软件再打开后，刚才修改的旁白没有保存。

AI 应将反馈关联到需求与任务，更新规格或排查问题，完成后报告实际验证结果。

## 常用表达

| 想做什么 | 可以直接说 |
|---|---|
| 查看当前状态 | 阅读项目进度，告诉我完成了什么、有什么问题、下一步是什么。 |
| 修改需求 | 我想调整这个功能：……请整理影响并更新文档。 |
| 了解一个决定 | 解释这个方案的取舍，以及它对使用体验、费用和隐私的影响。 |
| 检查完成情况 | 对照需求和验收条件，检查这个功能是否完成，并提供验证证据。 |
| 暂停工作 | 先停在这里，记录当前状态和后续步骤。 |
| 继续工作 | 阅读项目文档和当前进度，接着推进 LifeStory Studio。 |

## 换聊天后如何继续

在可以访问本项目文件的新聊天中，说：

> 阅读 README.md、AGENTS.md、项目进度、PRD 和决策记录，先说明当前状态，再继续已授权的下一步。

文档保存的是项目状态和决定，帮助新的会话接续工作。它不会自动安排定时任务或在没有会话时持续开发。

## 测试如何控制投入

我们按 [测试边界](process/TESTING_POLICY.md) 执行。普通文案、标点和装饰样式不会机械新增测试；数据、隐私、引用和关键交互需要保护。一组相关修改完成后只运行相关检查，不要求每次编辑前先测试，正式发布时再做必要的完整回归。验收标准可以用自动化、实际操作或人工评审验证，无需每条都写成用例。

## 文档如何保持一致

你在聊天中作出明确决定或提出修改后，AI 应同步维护：

- 产品行为变化：更新 PRD 及受影响的功能规格。
- 关键选择：更新决策记录，注明依据与影响。
- 工作完成、受阻或验证结果：更新项目进度。
- 工作流程或你的协作方式变化：更新本手册及相关协作规则。

未确定的内容保留为待决策；未执行的检查不能写为通过。你的最新明确指示优先，文档应随之更新。

## 代码如何保存到远程

项目远程仓库为 [NotionNest/LifeStory-Studio](https://github.com/NotionNest/LifeStory-Studio)，现为公开仓库。你无需手动操作 Git，直接说明要在分支开发、提交、创建 PR 或合并即可。详细约定见 [Git 流程](process/GIT_WORKFLOW.md)。本次完成初始化与首次推送，之后按任务分支推进；CI 的双平台编译不替代实际桌面验收。

## 接下来如何推进

产品方向、主要范围及 DEC-12～DEC-15 技术与测试方案均已确认。开发骨架已建立，可以按 [开发环境说明](development/ENVIRONMENT.md) 启动，当前可使用文字记录、自动保存，以及历史查看、重要标记和恢复为新版本；已通过 macOS 对应链路验证，Windows 实机仍待验收。后续按资料库任务顺序推进；剩余范围和 Windows 验证继续在决策表和项目进度中跟进。

## 当前桌面记录操作

新建记录后直接书写即可，无需点击保存。停止输入约 800 毫秒自动写入本机，持续输入最长 2 秒发起写入；以“已保存到本机”为准。需要时仍可按 ⌘S/Ctrl+S 立即写入。

短暂写入失败会自动重试并保留编辑内容。磁盘空间不足需处理后重试；版本冲突不会自动覆盖。只有最新内容尚未落盘时，离开才会要求处理，可重试、主动另存或明确放弃。日期暂时清空不影响正文保存，界面提示日期待补充。

正常重开直接显示已保存的最新内容，不需要先恢复草稿。旧版遗留草稿仍会对照预览供你选择。历史仅在重新进入编辑时固定上一轮内容；写作过程中持续保存当前内容，不生成历史检查点。空白或内容未变时重复打开不增加历史。未写入磁盘的最后输入无法保证恢复。

本次调整的实现与证据见 [保存模型调整](development/SAVING_MODEL_REVISION.md)。

## 日常 Git 操作（2026-10-16 更新）

日常任务从 develop 开分支，完成后通过 PR 回 develop；准备发版时从 develop 建 release/<版本>，验收后合入 main，再把 main 回合 develop。任务通常 squash，长期分支之间使用 merge。你只需说“在 develop 基础上完成任务并创建 PR”，不必自行执行命令；合并与对外发布分别授权。

每个 PR 看 CI Gate；文档变更跳过昂贵任务，应用变化按改动内容执行轻量检查；完整双平台验证集中在候选、手动完整检查及生产紧急修复。候选包在 release 分支生成，使用独立 Preview 数据目录，正式发布还需签名和安装验收。仓库已按你的要求改为公开；main、develop、release/* 的服务器保护已启用，必须经 PR、CI Gate 成功且基于最新目标分支验证，禁止强推和删除，没有管理员绕过名单。批准人数为 0，避免单人项目无法合并；合并方式仍按分支约定选择。完整规则见 [Git 流程](process/GIT_WORKFLOW.md)。


### CI 检查出现红灯时

代码更新或修改 PR 目标分支会重新检查；仅改标题/说明不会重跑应用验证或取消原任务，会用轻量门禁核实当前提交与目标的完整验证结果；若仍在运行就等待它，原验证失败时仍不允许合并。普通说明文档可跳过应用任务，新目录或配置不会被默认当成文档。release 合入 main 必须已有匹配的成功候选：若 Checks 比候选先结束而失败，先等候选成功，再重新运行该 PR 的失败 Checks；若合并内容变了，先同步 release 并重新构建候选。合并后不再重复运行来源核对，PR 保护由服务器执行。


### 日常 PR 为什么更快

2026-10-19 起，CI 方案按改动选择检查：纯前端只做类型、交互和前端构建；Rust/存储改动做一次 macOS Rust 检查；图片工具改动只做一次 Ubuntu 图片验证。说明文档只经过门禁。普通 develop/release 修复 PR 不编译完整双平台桌面应用。预发布候选和手动完整检查执行双平台验证；正式 release 合入 main 复用匹配候选结果，生产 hotfix 则完整检查。规则须在 CI 修改 PR 合入后生效，不会缩短已经完成的旧运行。

### git 分支流转
``` mermaid
flowchart LR
    D[develop] --> F[任务分支]
    F -->|PR · Squash| D
    D --> R[release/版本]
    R --> X[候选修复分支]
    X -->|PR| R
    R -->|验收后 PR · Merge| M[main]
    M -->|PR · Merge 回流| D
    M --> H[hotfix/紧急修复]
    H -->|PR| M
```


### PR 与 commit 使用中文

后续 PR 标题和描述、commit 标题和正文均使用中文。`fix(library): 修复切换记录时的保存边界` 这样的类型前缀保留英文，具体说明使用中文。合并时也检查最终提交文案。此规则已写入 AI 协作规则与 Git 流程，无需你每次提醒；历史提交不改写。
